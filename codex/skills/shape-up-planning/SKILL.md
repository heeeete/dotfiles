# Shape Up 기획

사용자의 아이디어를 Shape Up 형식의 한글 기획 문서로 정리한다.

## 트리거 규칙

- 사용자가 이 스킬을 명시적으로 호출했을 때만 사용한다.
- 일반적인 "기획서 써줘", "아이디어 정리해줘", "PRD 만들어줘" 요청에는 사용하지 않는다.

## 원칙

- 사용자의 말이 모호하면 바로 작성하지 않는다.
- 이해가 안 되는 부분은 이해될 때까지 짧고 구체적으로 질문한다.
- 사용자가 말하지 않은 기능, 범위, 요구사항을 임의로 추가하지 않는다.
- Shape Up 기획에 필요한 최소 요소만 남긴다.
- 과한 PRD, 상세 스펙, 일정표, 태스크 목록으로 확장하지 않는다.
- 기획 문서는 너무 길게 쓰지 않고, 사람이 봤을 때 한눈에 들어오게 일목요연하게 작성한다.
- 최종 결과는 Markdown 원본으로 작성한다.

## 도메인 언어 규칙

- 최종 문서에는 함수명, 변수명, 타입명, API 필드명, DB 컬럼명, capability 같은 내부 식별자를 직접 쓰지 않는다.
- 사용자가 내부 식별자로 설명하더라도, 기획 문서에서는 사용자와 제품 관점의 도메인 언어로 바꿔 쓴다.
- 기술 식별자가 의사결정에 꼭 필요하면 문서에 바로 쓰지 말고, 도메인 표현으로 어떻게 부를지 먼저 확인한다.

예:
- `canManageFinance capability` → `재무 영역을 사용할 수 있는 권한`
- `새 role을 만들지 않는다` → `권한 종류를 새로 늘리지 않는다`
- `admin/member` → `어드민/일반 멤버`
- `권한 체크 함수에서 처리한다` → `재무 권한은 한 곳에서 판단한다`

## 진행 방식

1. 사용자의 설명에서 다음 항목을 파악한다.
   - 해결하려는 문제
   - 대상 사용자
   - 원하는 변화
   - Appetite
   - 대략적인 해결 방향
   - 제외할 범위
   - 위험하거나 헷갈리는 지점

2. 불명확한 항목이 있으면 질문한다.
   - 한 번에 너무 많이 묻지 않는다.
   - 막히는 핵심 질문부터 묻는다.
   - 사용자의 답변이 여전히 모호하면 다시 묻는다.

3. 충분히 이해되면 Shape Up 문서를 작성한다.

## 필수 섹션

최종 문서는 아래 섹션만 사용한다.

```md
# 기획 제목

## Problem

어떤 문제가 있고, 왜 지금 해결해야 하는지 적는다.

## Appetite

이번 문제에 어느 정도 시간을 쓸지 적는다.

예:
- 2일
- 1주
- 2주
- 6주

## Solution

어떤 방향으로 해결할지 적는다.

상세 구현 목록이 아니라, 만들 결과의 형태와 핵심 동작을 설명한다.

## Rabbit Holes

빠지기 쉬운 함정, 과해지기 쉬운 구현, 미리 조심해야 할 위험을 적는다.

## No-gos

이번 범위에서 하지 않을 것을 적는다.
```

## 질문 규칙

다음 중 하나라도 불명확하면 질문한다.

- 문제가 무엇인지 불명확함
- 누가 쓰는지 불명확함
- 성공 상태가 불명확함
- Appetite이 없음
- 해결 방향이 너무 넓음
- 제외 범위가 없음
- 사용자의 표현이 모호해서 서로 다른 해석이 가능함

질문은 이렇게 한다.

```md
여기서 아직 헷갈리는 게 있어요.

1. 이 기획의 대상 사용자는 누구인가요?
2. Appetite은 어느 정도로 볼까요? 예: 2일, 1주, 2주, 6주
3. 이번에 절대 하지 않을 범위가 있나요?
```

## 출력 규칙

- 최종 문서는 한국어로 작성한다.
- 문체는 간결하게 쓴다.
- 사용자의 의도는 살리되, 함수명/필드명/내부 식별자는 도메인 언어로 치환한다.
- 섹션마다 핵심만 남기고, 불필요한 배경 설명은 줄인다.
- 긴 문단보다 짧은 문단과 bullet을 우선 사용한다.
- 확정되지 않은 내용은 확정처럼 쓰지 않는다.
- 불확실한 부분이 남아 있으면 문서 작성 전에 질문한다.
- 사용자가 “일단 초안으로 써줘”라고 하면, 불확실한 부분은 `[확인 필요]`로 표시하고 초안을 작성한다.
