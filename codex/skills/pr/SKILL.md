# PR 공유 메시지 작성

현재 PR을 팀원이 빠르게 이해할 수 있는 공유 메시지를 작성한다. `$pr 공유` 또는 `$pr 공유 #1049`처럼 호출하며, PR URL도 지정할 수 있다. `$pr`만 호출해도 공유 메시지를 작성한다.

## 확인 절차

1. 사용자가 PR 번호나 URL을 지정하면 해당 PR을 사용한다.
2. 별도 지정이 없으면 현재 저장소와 브랜치에 연결된 PR을 찾는다. 대화에서 확인한 PR도 활용하되, 여러 후보가 있어 대상을 정할 수 없을 때만 질문한다.
3. PR 제목과 본문뿐 아니라 대상 브랜치 대비 실제 변경 내용도 확인한다.
4. 변경 이유, 사용자가 겪던 문제, 달라진 동작과 팀원이 알아야 할 핵심을 선별한다.
5. PR을 찾을 수 없거나 제품 의도를 판단할 정보가 부족할 때만 질문한다.

PR과 저장소는 읽기 전용으로 확인한다. 메시지 초안만 제공하며 PR 본문 수정, 댓글 작성, 커밋·푸시, 팀원에게 메시지 전송은 수행하지 않는다.

## 작성 형식

다음 구조를 기본으로 사용하되, 변경 규모에 맞춰 문단과 항목 수를 조절한다.

```text
PR : [PR 제목](PR 링크)

<팀원에게 변경 내용을 공유하는 자연스러운 문장>

<변경 배경과 기존 문제, 달라진 동작 설명>

작업 내용

- <핵심 변경>
- <핵심 변경>

<확인된 검증 결과나 머지 상태가 공유에 필요하면 짧게 추가>
```

본문에 API 엔드포인트를 적었다면 메시지 마지막에 각 API의 역할을 덧붙인다. API가 등장하지 않으면 이 항목은 생략한다.

```text
API 역할

- `/example/path`: 이 API가 담당하는 역할
```

## 작성 원칙

- 첫 줄은 실제 PR 제목과 링크를 사용한 `PR : [제목](링크)` 형식으로 쓴다.
- 한국어로 자연스럽고 직접적으로 공유한다. 기본 문안에 리뷰·승인 요청, 확인 부탁, 리뷰어에게 하는 지시는 넣지 않는다.
- 버그 수정은 어떤 조건에서 무엇이 실패했는지와 수정 후 동작을 구체적으로 설명한다. 실제 처리 실패를 단순한 혼동이나 표현 개선으로 축소하지 않는다.
- 파일별 변경 목록은 피하고, 구현 방식과 그 효과를 의미 있는 변경 축으로 묶는다. 비개발 팀원도 이해할 수 있도록 불필요한 내부 용어를 줄인다.
- 간단한 변경은 짧게 쓴다. 항목 수를 억지로 맞추거나 이 대화의 작업 과정·시행착오를 나열하지 않는다.
- 테스트 수치와 결과는 확인된 것만 쓴다. PR 생성·머지·배포·실제 화면 확인은 서로 구분하고, 머지됐다는 이유로 운영에 적용됐다고 쓰지 않는다.
- API 경로가 필요하면 정확한 경로를 사용하고 임의의 별칭으로 대체하지 않는다.
- 최종 메시지 전체를 네 개의 백틱으로 시작하고 끝나는 `md` 코드블록으로 감싸 Markdown 원본으로 출력한다. 내부 코드블록이 있으면 바깥 fence는 내부보다 길게 쓴다.
- 사용자에게 전달할 공유 메시지만 출력하고 작업 과정이나 별도 설명은 덧붙이지 않는다.
