# PR 본문 작성

리뷰어가 첫 화면에서 변경 결과, 영향 범위, 위험도, 머지 판단 근거를 파악하고 본문에서 구현 방식과 버그 원인을 확인할 수 있는 PR 본문을 작성한다.

## 근거 확인

- 현재 diff, 관련 커밋, 기존 PR 본문과 대화에서 확인된 제품 의도를 바탕으로 작성한다.
- 테스트, 빌드, 정적 검사, 브라우저 확인은 실제 실행 결과만 기록한다.
- 이슈 번호, 화면 이미지, 테스트 결과, 영향 범위를 추측하거나 만들어내지 않는다.
- PR 본문 작성은 PR 생성·수정 권한을 뜻하지 않는다. 원격 상태 변경은 사용자의 명시적 요청과 적용 중인 승인 규칙을 따른다.

## 본문 구성

다음 순서를 기본으로 사용한다.

### 1. 한눈에 보는 요약

GitHub `NOTE` 알림을 하나만 사용한다. 첫 문장은 사용자 또는 시스템 관점의 결과, 둘째 문장은 변경 이유나 해결된 문제를 설명한다. 구현 과정이나 파일 목록으로 시작하지 않는다.

### 2. 상태표

요약 바로 아래에 `영향 범위`, `위험도`, `머지 상태`, `판정 근거`를 한 행으로 표시한다. 헤더와 데이터 행은 각각 정확히 네 개 셀로 작성하고 빈 셀을 두지 않는다.

- 영향 범위는 실제로 바뀐 제품·서비스·모듈을 인라인 코드로 표시한다.
- 위험도는 다음 기준으로 판단한다.
  - `낮음`: 국소적인 변경이며 인증, 데이터, 공개 계약, 배포 동작에 영향이 없음
  - `보통`: 여러 모듈 또는 사용자 흐름·상태 동작이 함께 바뀜
  - `높음`: 인증·권한, 데이터 마이그레이션, 공개 API 계약, 배포 또는 운영 데이터에 영향이 있음
- 머지 상태는 다음 중 하나만 사용한다.
  - `🟢 바로 머지 가능`: 관련 검증이 통과했고 알려진 차단 요소가 없음
  - `🟠 추가 검증 권장`: 필요한 환경·실계정·브라우저 검증 등이 남아 있음
  - `🔴 머지 보류`: 실패한 검사나 해결되지 않은 차단 요소가 있음
- `판정 근거`에는 해당 상태를 고른 구체적 이유를 한 문장으로 적는다. 통과한 핵심 검증, 남은 검증, 실패한 검사나 차단 요소 중 판정에 직접 영향을 준 내용을 명시하고 `검증 필요`처럼 모호하게 쓰지 않는다.
- 주관적인 `신뢰도` 필드는 사용하지 않는다.

### 3. 달라진 점

외부 동작이나 시스템 흐름이 바뀌었다면 `항목 | 변경 전 | 변경 후` 비교표를 사용한다.

- 사용자·시스템이 관찰할 수 있고 리뷰 판단에 필요한 차이를 빠짐없이 정리한다. 비슷한 내용은 하나의 변경 축으로 묶되, 개수 제한 때문에 의미 있는 변경을 생략하지 않는다.
- 각 셀은 한 문장으로 쓰고 파일명, 함수명, 구현 순서를 나열하지 않는다.
- 신규 기능의 기존 상태가 실제로 없었을 때만 `지원하지 않음`처럼 표현한다.
- 비교표가 사실을 억지로 단순화하는 내부 리팩터링이라면 표를 만들지 않는다. 사용자에게 보이는 동작 변화가 없음을 한 문장으로 밝히고 `## 내부 변경`에 의미 있는 구조 변화만 정리한다.

### 4. 버그 원인

버그 수정 PR에서만 `## 버그 원인`을 별도 섹션으로 추가한다.

- 사용자가 겪은 증상을 반복하는 대신 어떤 조건에서 왜 잘못된 동작이 발생했는지 설명한다.
- `발생 조건`과 `근본 원인`을 구분하고, 코드나 재현 결과로 확인되지 않은 원인을 단정하지 않는다.
- 원인이 아직 확정되지 않았다면 `추정 원인`이라고 밝히고 판단 근거를 함께 적는다.
- 일반 기능 추가, 리팩터링, 문서 변경에서는 이 섹션을 생략한다.

### 5. 구현 방식

`## 구현 방식`은 항상 포함한다. `달라진 점`에서 설명한 결과가 어떤 구조나 흐름으로 만들어졌는지 리뷰 판단에 필요한 내용을 빠짐없이 정리한다.

- 각 항목은 `달라진 점` 또는 `내부 변경`의 변경 축과 대응되게 작성한다.
- 비슷한 구현은 하나의 변경 축으로 묶되, 개수 제한 때문에 의미 있는 구현을 생략하지 않는다.
- 데이터 흐름, 상태 갱신, API 계약, 예외 처리처럼 리뷰어가 구현을 이해하는 데 필요한 메커니즘을 설명한다.
- 파일명과 함수명은 설명에 꼭 필요할 때만 사용하고, 파일별 변경 목록이나 구현 순서를 나열하지 않는다.
- 버그 수정에서는 원인을 차단하는 해결 원리가 드러나게 작성한다.

### 6. 검증

`## 검증`은 항상 포함한다.

- `✅` 통과, `❌` 실패, `⏭️` 미실행을 사용한다.
- 명령어는 인라인 코드로 표시하고 결과를 짧게 덧붙인다.
- 미실행 검증은 숨기지 말고 이유를 함께 적는다.
- 실패한 검증이 있으면 머지 상태를 `머지 보류`로 표시한다.

### 7. 조건부 섹션

필요할 때만 다음 섹션을 추가한다.

- `## 리뷰 포인트`: 비자명한 의사결정, 위험 구간, 집중해서 볼 동작이 있을 때
- `## 화면`: 실제 UI 변경이 있고 사용할 수 있는 이미지가 있을 때. 전후 이미지가 모두 있으면 표로 비교한다.
- `<details>`: 긴 기술 설명, 제약, 구현 세부사항이 리뷰에 실제로 필요할 때
- `Closes #...`: 확인된 관련 이슈가 있을 때

내용이 없는 조건부 섹션은 `없음`으로 채우지 말고 생략한다.

## 기본 템플릿

```markdown
> [!NOTE]
> **{사용자 또는 시스템 관점에서 달라진 결과}**
> {변경 이유 또는 해결된 문제}

| 영향 범위 | 위험도 | 머지 상태 | 판정 근거 |
| --- | --- | --- | --- |
| `{영역}` | {낮음·보통·높음} | {🟢 바로 머지 가능·🟠 추가 검증 권장·🔴 머지 보류} | {해당 상태를 선택한 구체적 이유} |

## 달라진 점

| 항목 | 변경 전 | 변경 후 |
| --- | --- | --- |
| {동작 또는 흐름} | {기존 상태} | {변경된 상태} |

## 구현 방식

- **{변경 축}**: {결과를 만든 핵심 구조 또는 처리 흐름}

## 검증

- ✅ `{실행 명령}` — {결과}
- ⏭️ {미실행 검증} — {이유}

## 리뷰 포인트

- {집중해서 확인할 내용}
```

버그 수정 PR에서는 `## 달라진 점`과 `## 구현 방식` 사이에 다음 블록을 추가한다.

```markdown
## 버그 원인

- **발생 조건**: {문제가 나타나는 조건}
- **근본 원인**: {잘못된 동작을 만든 원인과 인과관계}
```

## 표현 규칙

- 사용자가 다른 언어를 요청하지 않으면 명확하고 간결한 한국어로 작성한다.
- PR 제목을 본문에서 반복하지 않는다.
- 커밋별·파일별 변경 목록, 시행착오, 장황한 구현 일지는 기본 본문에 넣지 않는다.
- 첫 화면을 복잡하게 만드는 장식용 이모지와 연속 알림 박스를 사용하지 않는다. 이모지는 상태 표시에만 사용한다.
- 기존 PR 본문을 수정할 때는 사용자가 유지하길 원하는 내용과 확인된 링크를 보존한다.
