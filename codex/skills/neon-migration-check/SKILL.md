# Neon 마이그레이션 점검

마이그레이션 파일별로 **이력에 기록되었는지**와 **현재 DB에 변경 결과가 남아 있는지**를 구분한다. 기록이 없다는 이유만으로 미적용이라고 판정하지 않는다.

## 대상과 범위

- 현재 저장소의 지침, Drizzle 설정, 마이그레이션 러너를 읽어 SQL 경로와 이력 저장 방식을 확인한다. `.env` 전체나 접속 비밀번호를 출력하지 않는다.
- 사용자가 지정한 Neon 연결을 우선한다. 연결 도구의 실제 스키마를 확인하고 프로젝트 → 브랜치 → 데이터베이스를 조회해 대상을 확정한다. SQL 호출에는 확인한 프로젝트 ID·브랜치 ID·DB 이름을 명시해 기본 브랜치로 잘못 연결되지 않게 한다.
- 프로젝트나 브랜치가 여러 개여서 대상을 확정할 수 없으면 필요한 선택만 질문한다. 대상에 접근할 수 없으면 로컬 조사 결과와 원격 확인 한계를 구분한다.
- `0110 이후`처럼 기준 번호를 받은 경우 이후 파일을 조사하고, 기준 파일도 별도로 확인해 포함 여부를 답변에서 밝힌다. 범위가 없으면 전체 마이그레이션을 대상으로 한다.
- 이전 대화의 미적용 목록은 현재 상태의 근거가 아니다. 특히 사용자가 적용했다고 알려준 뒤 재점검을 요청하면 다시 조회한다.

### Bluepin ERP에서의 탐색 단서

현재 저장소가 `bluepin-erp` / `bluepin_erp`일 때만 다음 정보를 시작점으로 사용한다. 경로와 원격 이름은 조회로 다시 확인하며, 사용자가 지정한 대상을 우선한다.

| 항목 | 위치 또는 이름 |
|---|---|
| Neon 프로젝트 | `bluepin-erp` |
| 개발 브랜치 / DB | `dev` / `neondb` |
| SQL / journal | `packages/db-tools/drizzle/` / `meta/_journal.json` |
| 설정 / 러너 | `packages/db-tools/drizzle.config.ts` / `packages/db-tools/src/migrate.ts` |
| 업무 스키마 / 기본 이력 후보 | `bluepin` / `drizzle.__drizzle_migrations` |

다른 저장소에는 이 이름과 경로를 기본값으로 적용하지 않는다.

## 로컬 파일과 적용 이력 대조

1. `rg --files`로 SQL과 journal을 찾는다. 본 마이그레이션과 `.rollback.sql`, `.verify.sql`, `.precheck.sql` 등 보조 파일을 분리한다. 보조 파일은 적용 대상 개수에 넣지 않는다.
2. journal의 `tag`, `when`, 순서를 읽고 실제 SQL 파일 목록과 대조한다. 번호 공백 자체는 미적용 파일이 아니다. 파일은 있는데 journal에 등록되지 않았거나 등록된 파일이 없으면 별도로 보고한다. `idx`와 파일 번호가 같다고 가정하지 않는다.
3. 각 대상 SQL의 원문을 읽고, 러너와 같은 방식으로 SHA-256을 계산한다. Drizzle의 일반적인 방식은 파일 원문 전체의 SHA-256이며 주석·공백을 제거하거나 statement 단위로 나누어 해시하지 않는다.
4. 실제 이력 테이블 위치와 컬럼을 확인한 뒤 필요한 이력을 SELECT로 읽는다. 기본 후보는 `drizzle.__drizzle_migrations`지만 설정을 우선한다. 단순히 최근 몇 행만 보고 전체 범위의 기록 유무를 확정하지 않는다.
5. 로컬 해시와 journal 시각을 각각 비교한다. Drizzle의 `created_at`은 보통 journal의 `when` 값이며 실제 실행 시각으로 해석하면 안 된다. 해시와 시각이 서로 다른 파일을 가리키거나 시각만 일치하면 불일치로 표시한다.

## 실제 DB 반영 상태 확인

대상 SQL과 관련 후속 SQL을 읽어 **현재 남아 있어야 하는 결과**를 만든 뒤 카탈로그와 대조한다. 이력이 일치해도 현재 객체가 사라지거나 변경되었을 수 있다.

- 테이블: `to_regclass`, `pg_class`, `pg_namespace`로 스키마까지 확인한다.
- 컬럼: `information_schema.columns` 또는 `pg_attribute`로 존재·타입·NULL 허용·기본값을 비교한다.
- 제약조건: `pg_constraint`와 `pg_get_constraintdef`로 CHECK, UNIQUE, FK 대상·삭제 동작을 비교한다.
- 인덱스: `pg_indexes`로 컬럼 순서, UNIQUE 여부, 부분 인덱스 조건까지 확인한다. 이름만 같은 것으로 충분하다고 보지 않는다.
- 삭제·이름 변경: 뒤 번호에서 의도적으로 제거·대체한 객체를 앞 번호의 미적용 근거로 삼지 않는다. 예를 들어 0117에서 만든 중간 테이블을 0118이 삭제했다면 0118의 최종 구조로 판단한다.
- 데이터 이관·백필: 현재 데이터로 확인 가능한 불변식을 SELECT로 검사한다. 필요한 건수·불일치 수 위주로 조회하며 불필요한 업무 데이터는 노출하지 않는다. 구조만으로 과거 데이터 이관 실행까지 증명할 수 없다면 `구조 반영 확인, 데이터 이관 여부 확인 불가`로 적는다.
- 검증 SQL은 먼저 읽는다. 필요한 검사를 읽기 전용 SELECT로 옮길 수 있으면 그렇게 한다. 파일 이름이 `verify`라는 이유로 검토 없이 실행하지 않는다.

필요한 변경 결과가 일부만 있거나 이력과 실제 상태가 충돌하면 `부분 반영/불일치`로 남긴다. 권한 부족·조회 실패를 객체 부재로 해석하지 않는다.

## 점검 경계

이 스킬은 조회만 수행한다. 점검 요청으로 `db:migrate`, `db:push`, DDL/DML, 이력 INSERT·UPDATE, 브랜치 생성·리셋, `.env` 수정까지 진행하지 않는다. 사용자가 별도로 적용을 요청하면 이 점검 결과와 의존관계를 넘겨 후속 작업으로 처리한다.

기록이 뒤처져 있으면 일괄 재실행을 권하지 않는다. 이미 반영된 CREATE·ALTER가 충돌할 수 있고, `IF NOT EXISTS`도 데이터 변경의 재실행 안전성을 보장하지 않는다.

## 결과 전달

첫 문장에 대상 `프로젝트 → 브랜치 → DB`와 미적용 파일 수를 적는다. 미적용·부분 반영 파일을 우선해 `파일 | 상태 | 확인 근거` 표로 보여주고, 파일은 절대 경로 링크로 연결한다. 기준 번호 자체는 별도로 구분한다.

나머지는 간결하게 정리한다.

- 반영이 확인된 번호와 번호 공백·journal 미등록 파일.
- 이력 누락, 해시 불일치, 데이터 이관 검증 한계가 있다면 해당 근거.
- 선행 마이그레이션이 필요한 파일의 의존관계.
- 조회만 수행했으며 마이그레이션은 실행하지 않았다는 사실.

이력이 없지만 구조가 일치하면 `실제 구조 반영 확인(이력 없음)`으로 표현한다. 과거 SQL 실행 자체가 증명되었다고 단정하거나 확인하지 않은 범위를 완료 처리하지 않는다.
