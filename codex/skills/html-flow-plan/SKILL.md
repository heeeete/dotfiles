# 화면 예시 HTML 기획서

비개발자가 클릭하지 않고도 **어느 화면에서 무엇을 하고, 결과가 어디에 반영되는지** 이해하는 기획서를 만든다. 기본은 ‘누르기 전 → 입력 화면 → 저장 후’를 펼쳐서 읽는 정적 문서다. 긴 개발 명세보다 짧은 설명과 구체적인 화면 예시를 우선한다.

## 기준 결과물

[assets/reference.html](assets/reference.html)은 사용자가 요청한 전후 화면 비교와 화살표 구성을 반영한 단독 HTML 기획서다. 새 문서를 만들 때 이 파일의 스타일과 화면 틀을 확인하고 필요한 부분을 복사해 사용한다. 기획서를 만들 때는 스킬 안의 원본을 수정하지 않는다.

- 유지할 특징: 옅은 회색 바탕, 하얀 화면 패널, 절제된 강조색, 짧은 해요체 설명, 전후 화면을 펼쳐 보여주는 구성, 행동 이름이 붙은 화살표.
- 그대로 고정하지 않을 것: Bluepin 브랜드, AS라는 업무, 운영 정책, 단계 수, 메뉴 위치, 가상 데이터, 날짜. 새 요청의 맥락과 프로젝트 가이드로 대체한다.
- 현재 프로젝트의 디자인 가이드와 사용자가 지정한 표현이 참고 파일보다 우선한다. 가이드가 없으면 참고 파일의 차분한 업무 도구 스타일을 기본값으로 쓴다.
- 기존 기획서를 조금 수정하는 요청은 해당 부분만 바꾼다. 사용자가 승인한 구성과 인터랙션을 다시 디자인하지 않는다.

## 먼저 실제 서비스와 연결 지점을 확인한다

기존 프로젝트가 있으면 요청에 필요한 범위에서 메뉴·라우트, 목록·상세 화면, 주요 처리 액션, 데이터 항목을 읽는다. UI를 변경할 때는 해당 프로젝트의 디자인 가이드를 먼저 읽는다. 코드만 확인했다면 실행 화면을 직접 확인한 것처럼 설명하지 않는다.

확인할 내용은 세 가지다.

1. **누가, 어디서 시작하는가:** 이용자와 실제 진입 메뉴.
2. **기존 흐름에서 어디를 더하는가:** 새 페이지, 기존 상세의 추가 영역, 기존 완료 폼 등.
3. **무엇이 어디에 반영되는가:** 상태, 수량, 금액, 이력 등의 변화.

두 기능이 연동된다는 이유로 같은 메뉴 아래에 배치하지 않는다. 기존 내비게이션과 사용자가 정한 소속을 따른다. 확인되지 않은 배치나 정책은 제안으로 표시한다. 결과를 바꾸는 중요한 정보가 비어 있고 근거로도 판단할 수 없을 때만 짧게 묻는다.

사용자가 먼저 이해·분석만 요청했다면 그 범위까지 진행한다. HTML 생성 요청이 있으면 기획서를 만들고, 실제 서비스 구현은 별도 요청 범위로 둔다.

## 문서 구성

참고 파일의 읽는 순서를 기본으로 하되, 기능의 실제 흐름에 맞춰 섹션 수와 화면 배치를 조정한다.

- **짧은 도입:** 문서명, 현재 날짜, 기능이 해결할 일과 범위를 1~2문장으로 설명한다.
- **전체 흐름:** 주요 단계와 변화하는 값 또는 상태를 한 줄로 보여준다. 각 단계에서 해당 화면으로 이동할 수 있게 한다. 번호는 실제 순서가 있을 때 쓴다.
- **화면 예시:** 단계별 짧은 설명 다음에 ‘누르기 전 → 입력 화면 → 저장 후’를 필요한 만큼 나란히 배치한다. 실제 서비스에서 모달이나 조건부 항목으로 나타나는 내용도 문서에는 펼쳐 보여준다. 메뉴·화면 제목·표·상태·폼·주요 행동이 보이도록 하고, 새 화면과 기존 화면에 추가되는 부분을 구분한다.
- **화면 연결:** 순서가 있는 화면 사이에는 화살표 아이콘과 ‘방문 등록 누르기’, ‘결과 저장하기’처럼 다음 화면으로 이어지는 행동 이름을 붙인다. 넓은 화면에서는 오른쪽, 세로로 쌓인 화면에서는 아래로 연결한다. 같은 결과를 보여주는 두 서비스 화면처럼 병렬 관계인 곳에는 순서 화살표를 붙이지 않는다.
- **결과 확인:** 핵심 입력 옆이나 다음에 변경 전후 값, 반영 대상, 남는 이력을 처음부터 보여준다. 계산이나 상태 변화도 예시 입력값과 계산된 결과를 함께 표시해 클릭 없이 비교할 수 있게 한다.
- **최소 운영 기준:** 사용자 결정에 영향을 주는 가정과 예외만 간단히 적는다. 별도 요청이 없으면 DB 설계, API 목록, 구현 일정으로 확대하지 않는다.

하나의 가상 사례를 처음부터 끝까지 이어서 쓴다. 같은 고객·요청 번호·품목·단위가 모든 화면에서 일치해야 한다. 실제 시스템과 연결되지 않은 예시임을 문서에 명확히 표시한다. 참고 파일의 날짜나 브랜드가 무관한 결과물에 남지 않게 한다.

## 화면 표현과 선택적 인터랙션

- 문서 안의 화면은 프로젝트의 실제 컴포넌트와 정보 밀도를 참고한다. 큰 홍보 문구나 장식 대신 업무 내용이 먼저 읽히게 한다.
- 색·폰트·간격을 CSS 변수로 정리한다. 강조색은 절제하고, 상태색은 의미가 있을 때만 쓴다. 화면 또는 폼마다 주요 채움 버튼 하나를 둔다.
- 표의 수량·금액은 단위와 자릿수를 맞추고, 변경 전후 값은 쉽게 비교되게 한다. 항목의 단위가 다르면 의미 없는 총합을 만들지 않는다.
- 화면 속 버튼과 입력칸은 정적 예시로 표현하고, 설명용임을 안내한다. 업무 버튼에 클릭 이벤트·포인터 커서·탭 포커스를 넣지 않는다. 핵심 내용을 탭 전환, 모달 열기, 저장 버튼 클릭 뒤에 숨기지 않는다.
- 각 화면은 해당 시점의 값이 채워진 장면으로 만든다. 입력 중인 값, 저장한 값, 완료 후 반영값을 구분하고, 화면 사이의 고객·수량·상태·이력이 일관되게 이어지도록 한다.
- 기본 문서의 JavaScript는 테마 전환·인쇄 같은 보조 동작에만 쓴다. 목차 이동은 앵커 링크로 제공하고, 본문과 전후 화면은 JavaScript 없이도 보이게 한다. 인쇄할 때도 모든 전후 화면을 포함한다.
- 좁은 화면에서는 패널을 순서대로 세로 배치하고 화살표도 아래로 바꾼다. 읽기 전용 넓은 표는 내부 스크롤을 허용하되, 핵심 입력 예시와 결과는 화면 안에 둔다. 프로젝트의 라이트·다크 토큰을 따르고 제목 계층과 항목 라벨을 유지한다.

사용자가 클릭해서 체험하는 데모를 명시적으로 요청한 경우에만 업무 버튼과 입력을 동작하게 만든다. 그때는 화면들이 같은 예시 상태를 공유하게 하고, 초기화와 필요한 입력 제한·완료 조건을 제공한다. 문서에 적은 규칙과 실제 동작이 일치해야 한다.

## 단독 파일로 전달한다

기본은 CSS와 필요한 보조 JavaScript를 포함한 **HTML 한 파일**이다. 외부 라이브러리, 서버, 빌드, API 연결 없이 파일을 열어 모든 화면 예시를 읽을 수 있게 한다. 외부 글꼴이 없어도 읽을 수 있게 대체 글꼴을 둔다. 필요한 이미지가 있으면 파일 안에 포함하거나, 단독 파일 요구와 충돌하는지 먼저 판단한다.

새 문서의 저장 위치는 사용자가 지정한 곳을 우선하고, 없으면 현재 사용자의 다운로드 폴더를 기본으로 한다. 예를 들어 `~/Downloads/<기능명>_기획서_<현재 날짜>.html`처럼 이름만 보고 찾을 수 있게 한다. 기존 문서 수정 시에는 별도 이동 요청이 없는 한 경로를 유지한다.

실제 앱 코드·DB·배포 설정을 바꾸지 않고 기획서만 만든다. 커밋·푸시·게시·배포는 기획서 생성에 포함하지 않는다.

## 확인하고 마무리한다

새 문서나 화면 배치 변경은 브라우저를 사용할 수 있으면 데스크톱과 모바일 너비에서 묶어서 확인한다. 모든 전후 화면이 별도 조작 없이 보이는지, 화살표와 행동 이름이 읽는 순서에 맞는지 확인한다. 라이트·다크를 제공했다면 양쪽을 확인한다. 클릭형 데모를 요청받은 경우에만 핵심 정상 흐름과 중요한 입력 경계를 실행해 본다. 발견한 문제를 한 번에 수정하고 필요한 부분만 재확인한다. 단순 문구 수정에는 전체 흐름 재시험을 반복하지 않는다.

특히 **문서의 설명 → 입력 예시 값 → 결과 화면 → 원래 목록에 반영된 값**이 일치하는지 확인한다. 화면이 제대로 읽히는지, 제목 단계가 건너뛰지 않는지, 모바일에서 날짜·수량이 잘리지 않는지, 인쇄 시 결과 화면이 빠지지 않는지도 본다. 브라우저 검증을 못 했다면 실행 확인을 했다고 말하지 않는다.

문서를 열자마자 전체 흐름을 읽을 수 있게 정리하고, 검증 중 바꾼 임시 화면 크기·테마 설정은 되돌린다. 가능한 환경에서는 완성 파일을 미리보기로 연다. 답변은 파일 링크와 비교해 볼 핵심 전후 변화를 1~2문장으로 전달한다. 실제로 확인하지 않은 검증 결과나 기능을 주장하지 않는다.
